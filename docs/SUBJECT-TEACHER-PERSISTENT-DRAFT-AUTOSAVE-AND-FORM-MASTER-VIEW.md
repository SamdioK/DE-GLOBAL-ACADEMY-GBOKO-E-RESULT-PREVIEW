# Subject Teacher Persistent Draft Autosave and Form Master Read-Back

**Date:** 11 November 2026  
**Scope:** Supabase-backed Subject Teacher draft autosave, cross-device continuation, and Form Master visibility of subject score entries.

## 1. Root causes identified

The active Subject Teacher score sheet loaded existing rows from `public.results`, but its database write was only attached to the manual **Save scores as draft** button. Editing a score recalculated the row and did not immediately persist it to Supabase. The legacy score-entry path also called the shared `saveAllData()` routine, which is intentionally blocked for Subject Teacher accounts.

A second database mismatch was found: `public.results.total` is a PostgreSQL generated column, but the Subject Teacher write payload included `total`. PostgreSQL must calculate that value; clients must not send it in INSERT/UPSERT payloads.

At the time of this change, the live `public.results` table contained zero rows. Therefore, no existing Subject Teacher drafts were available to recover from the database.

## 2. Persistent autosave behaviour

The active Subject Teacher score-entry screen now:

1. Schedules a Supabase draft save after score edits, with a short debounce to avoid a network write for every keystroke.
2. Flushes the pending row save when the teacher leaves a score field.
3. Writes the current student's four assessment components to `public.results` using the established unique key: `student_id, subject_id, academic_session_id, term_id`.
4. Leaves the result status as `draft` and records the authenticated teacher as `entered_by`.
5. Omits the generated `total` column from the write payload; PostgreSQL calculates it.
6. Reads the saved row back from Supabase and checks the component values, generated total and draft status before showing **Draft saved**.
7. Shows a visible row-level saving, saved or failure status. A failed write is not presented as a successful save.
8. Retains the existing explicit **Save scores as draft** batch action as an additional manual save option.

The draft lives in Supabase, not in browser storage. It is therefore available when the same authorised teacher signs in again from another device, provided the assignment, session and term remain valid. Drafts do not expire after 40 days merely because time passes; normal school retention and result workflow controls still apply.

## 3. Access control

The existing `results` RLS policies were inspected. They allow an active Subject Teacher to insert drafts and to update only their own draft rows when a matching active teacher assignment exists for the same school, class, subject and academic session. The existing policies also permit the assigned teacher to read those result rows.

No broad RLS bypass or shared school-state write permission was introduced. Submitted, approved and published results remain protected from this draft-entry path.

## 4. Form Master View

The Form Master **View** tab now includes a read-only **Subject Scores Submitted by Subject Teachers** panel. It reads the assigned class's subject result rows for the active academic session and displays:

- Student name and admission number
- Subject and term
- CA1, CA2, CA3 and examination scores
- Generated total and grade
- Draft/submission status
- Last-saved timestamp

The view uses the Form Master's existing class-result read permission. It does not grant the Form Master permission to edit a Subject Teacher's scores.

This is the verified subject-score data foundation for the class result sheet/report-card layout. The report-card presentation and finalisation workflow should consume these official result rows, rather than relying on browser-only student objects.
